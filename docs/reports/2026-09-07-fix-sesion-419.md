### 2. `sessions` table + row-reuse reproduction

Table exists (pre-existing migration, `Nothing to migrate` on `php artisan
migrate`). Reproduced with `curl`'s cookie jar (`-b`/`-c` to the same file)
against `http://127.0.0.1:8000/tramite/preregistro`, run with `php artisan
serve` exactly as the user runs it:

- Request 1 → row count went from 1 → 4 (three stray earlier no-cookie-jar
  test requests each created their own row, as expected — a client that
  discards cookies always gets a new session).
- Request 2, **cookie sent back** → row count stayed at **4** — no new row.
- Decrypted the `laravel-session` cookie value from both requests
  (`Crypt::decryptString`, no `APP_KEY` exposed) — **same underlying session
  ID** (`...|Z3omIfC1ujO1ROQjOyfWKF8hBlLvAOA8rXyG04z0`) both times. The
  cookie's *ciphertext* differs on every response (expected — Laravel
  re-encrypts with a fresh random IV on every write), which is not evidence
  of a new session; the decrypted plaintext session ID is what matters, and
  it was stable.

**Conclusion: plain page-load session persistence works correctly.** A
client that returns its cookie is recognized and reuses its session row.
This directly rules out (a), (b), and (c) — a host/domain/secure-cookie
mismatch would have produced a *new* session ID on request 2, not the same
one.

### 3. Reproducing the actual 419 over HTTP

Session persistence being fine doesn't mean the reported bug doesn't exist
— so the real reproduction is the Livewire round-trip itself, not a plain
page GET. Using Laravel's own `Http` facade from `tinker` (to get identical
cookie/CSRF handling to a browser, not curl's manual header juggling):

1. `GET /tramite/preregistro` → `200`. Extracted `<meta name="csrf-token">`,
   the page's `Set-Cookie` headers, and the Livewire `wire:snapshot` JSON
   verbatim from the rendered HTML.
2. `POST /livewire/update` with that exact `Cookie` header, `X-CSRF-TOKEN`
   matching the page's token, and a real component snapshot + one field
   update (`calle`) — precisely what a browser's Livewire JS sends on a
   `wire:model.blur` blur event.

Result: **`419`**, but the body is not a CSRF error:

```json
{
    "message": "Livewire detected a release token mismatch. \nThis happens when a user's browser session has been invalidated by a new deployment.",
    "exception": "Livewire\\Exceptions\\LivewireReleaseTokenMismatchException",
    ...
}
```

A valid CSRF token and a valid, reused session cookie were both present on
this request, and it still failed — which independently confirms the CSRF
token itself was never the problem. Livewire renders this exception with
the exact same "This page has expired" browser dialog as a real CSRF 419,
which is why it reads identically to the user.

Traced further: `Livewire\Features\SupportReleaseTokens\ReleaseToken::verify()`
looks up the snapshot's component name in Livewire's `ComponentRegistry`
before comparing release tokens:

```php
try {
    $componentClass = app(ComponentRegistry::class)->getClass($snapshot['memo']['name']);
} catch (ComponentNotFoundException) {
    throw new LivewireReleaseTokenMismatchException;
}
```

Reproduced this lookup directly: the page's snapshot carries
`memo.name = "app.http.livewire.tramite.paso1-preregistro"`. Calling
`ComponentRegistry::getClass()` with that exact string throws
`ComponentNotFoundException: Unable to find component:
[app.http.livewire.tramite.paso1-preregistro]` — **every time**, in a fresh
request, regardless of cookies or CSRF.

**Root cause: Livewire 3's auto-discovery convention expects components
under `app/Livewire/`. This project deliberately keeps them under
`app/Http/Livewire/`** (a project-specific convention, documented in
`CLAUDE.md`'s architecture section). The initial page load works because
the route (`Route::get('/tramite/preregistro', Paso1Preregistro::class)`)
dispatches straight to the class — no name lookup needed. But the rendered
snapshot still carries a name auto-derived from the namespace
(`App\Http\Livewire\Tramite\Paso1Preregistro` → `app.http.livewire.tramite.paso1-preregistro`,
the literal `Http` segment included), and nothing ever registers that alias
back to the class with Livewire's component registry — `Livewire::component(...)`
is never called anywhere in the app. So **every single Livewire AJAX
request for this component fails, unconditionally**, in any environment,
regardless of session/cookie/CSRF configuration. This matches the reported
symptom exactly: idle, on-input-edit, and on-select all go through the same
`/livewire/update` endpoint and all hit this same unconditional failure.

### 4. `SESSION_LIFETIME`

`120` minutes — the framework default, not unusually short. Given the real
root cause has nothing to do with session state, this doesn't need
changing, and the "on idle" symptom isn't a slow session decay either —
it's simply that any Livewire interaction (including an idle-triggered one,
if any existed) hits the same unconditional registry-lookup failure.

## Verdict

**None of hypotheses (a)-(d) are supported by the evidence.** Session
persistence, cookie domain/host, secure-cookie flag, and session lifetime
all check out. This is hypothesis **(e) — something else**: a Livewire
component-naming/registration mismatch between this project's
`app/Http/Livewire/` convention and Livewire 3's `app/Livewire/`
auto-discovery, causing every Livewire AJAX request for
`Paso1Preregistro` to fail with a mislabeled "page expired" error, unrelated
to CSRF or sessions.

**Per this task's explicit instruction ("If the evidence fits none of
these, stop and report rather than guessing. Do not apply a speculative
fix.") and its stated out-of-scope list ("Any wizard, Domain, or
Application code"), no fix has been applied on this branch.** The actual
fix — registering the component with Livewire (either
`Livewire::component('tramite.paso1-preregistro', Paso1Preregistro::class)`
in a service provider, or moving the Livewire components to
`app/Livewire/` to match the framework's own convention) — touches the
wizard's Livewire code, which this task explicitly places out of scope.
Part 2 (the `.env`/`.env.example` session fix) and Part 3 (the setup-doc
session section) are not applicable — none of the environment variables in
question are implicated, and changing them per the task's Part 2 recipe
would not fix anything and would misrepresent the bug as resolved.

**Recommendation:** a follow-up task, explicitly scoped to touch
`app/Http/Livewire/` component registration (or to revisit whether that
convention should hold given it silently breaks every Livewire round-trip),
is needed to actually fix this. Happy to do it on request.
