## Decisions Log

Non-obvious calls made during setup that deviated from the PRD/doc as written — kept here so future work (and future-you) knows *why*.

- **Filament v4 instead of v3**: PRD's stack table said Filament 3, but `composer create-project laravel/laravel` pulled Laravel 13 (current stable), which resolves to Symfony 8 — incompatible with Filament 3's Symfony 6/7 requirement. User confirmed v4 over pinning Laravel back to v11. Filament v4 API is close enough to v3 that PRD's functional requirements (§6) aren't expected to need rework.
- **Livewire v4 instead of v3**: same cause — latest stable pulled by Composer, not pinned. Not yet verified against any Livewire-3-specific PRD assumptions (there don't appear to be any — PRD only references Livewire at the stack-choice level).
- **PostgreSQL 18 instead of 16**: was already installed on the machine; newer minor-compatible version, no reason to downgrade.
- **Monorepo, not nested-single-folder**: originally `git init` ran inside `app-laravel/`, leaving `docs/` outside version control. Moved git root to `sedeq-incorporacion/` so `docs/` (PRD, compendio, DDL — required "in the repository" per PRD §9) travels with the code.
- **Single Laravel app, not split repos/services**: considered and rejected splitting the Filament admin panel or the domain/validation layer into a separate package or repo. Independent architecture review (agents-development-architecture:backend-architect) confirmed: no team to isolate, no independent deploy/scaling need, DB schema as shared contract across repos would double migration overhead for one dev on a deadline. Recommended (and applied) tightening code-layer boundaries instead — `app/Domain/` for framework-agnostic business rules (the Motor de Validación is the concrete first case, since it's the piece Etapa 2/3 reuses across trámites), `app/Livewire`/`app/Filament` stay thin and call into it.
- **Migrations generated from raw DDL, not hand-translated Schema Builder**: 44 tables with many `CHECK` constraints Laravel's Schema Builder doesn't cleanly express. Each migration wraps the DDL's exact `CREATE TABLE` statement via `DB::unprepared()` instead — guarantees the schema matches the already-3NF-normalized, already-validated DDL exactly, per PRD §4 ("No rediseñar el esquema").
- **Tables stay in `public` schema, not a dedicated one**: considered and rejected. A custom schema earns its keep for multi-tenancy or isolating a second system sharing the DB cluster — neither applies now (single DB, single role, single tenant). If a future Etapa 2/3 piece (RecaudaNet integration, a reporting/analytics layer) ends up as a separate service on the same Postgres instance, schema that piece then, not the core tables preemptively.
- **Test DB switched from sqlite in-memory to a dedicated Postgres DB (`sedeq_incorporacion_testing`)**: `phpunit.xml` originally pointed tests at sqlite `:memory:`, per Laravel default. But the 44 domain-table migrations run raw Postgres DDL verbatim (`SMALLSERIAL`, etc., via `DB::unprepared()` — see the migrations decision above) to preserve `CHECK` constraints exactly; sqlite can't parse that DDL, so `RefreshDatabase` failed on the first domain-table migration for any test touching those tables. Fix: added `.env.testing` + updated `phpunit.xml`'s `<php>` block to use `pgsql` against a new dedicated `sedeq_incorporacion_testing` database (separate from dev `sedeq_incorporacion`, so tests never touch dev data). Verified: full suite (31 tests) passes against it. Tradeoff accepted: test runs need a reachable Postgres instance now, no longer fully self-contained — but the alternative (rewriting migrations to be sqlite-compatible) would have broken the "byte-for-byte DDL match" guarantee that's the whole point of the `DB::unprepared()` approach.
- **Seeder idempotency without schema changes, even when a table has no UNIQUE constraint**: `reglas_validacion` and `perfiles_profesionales` have no UNIQUE constraint in the source DDL, so `insertOrIgnore` alone doesn't prevent duplicates on a second run. An implementer subagent's first attempt at `perfiles_profesionales` fixed this by adding two partial unique indexes to that table's migration — rejected on review: migrations under `database/migrations/2026_01_01_*` are byte-for-byte DDL ports and must never be edited to work around a seeder problem (same principle as the migrations Decisions Log entry above). Both seeders instead use delete-then-insert scoped to what they're about to re-insert (by `nivel_educativo_id` for `reglas_validacion`, by `cargo_puesto_id` for `perfiles_profesionales`) — no schema change, verified zero drift from `ddl_sistema_incorporacion_v3.sql`.
- **Educación Física / trabajador social / prefecto staffing threshold set to "más de 60" (61), not "≥60" (60)**: COMPENDIO_MAESTRO is internally inconsistent — §5.1 says "≥60 alumnos"/"60 o más", §5.2 (the Acuerdos Secretariales text) says "más de 60". User confirmed 61 explicitly (2026-09-04) when raised during code review; §5.2's Acuerdos text is the more authoritative/later source. Documented inline in `ReglasValidacionSeeder`'s docblock so a future reader doesn't "fix" it back to 60 without new instruction.
- **`perfiles_profesionales` includes Secundaria's Director Técnico (7 profiles), but not the per-asignatura docente catalog**: the original plan excluded all of Secundaria from this seeder, reasoning the carrera catalog "vive en el PDF fuente." A whole-branch code review caught that this is only true for the per-asignatura docente catalog (hundreds of entries, genuinely not reproduced in COMPENDIO) — Director Técnico's 7 accepted profiles ARE fully specified in §5.1 line ~495. User confirmed (2026-09-04): add the 7 rows now (Educación Básica, Educación Media, Intervención Educativa, Pedagogía, Psicología Educativa, Ciencias de la Educación, Maestría en Educación, all `titulo_cedula`), raising the seeder's total from 80 to 87 rows.
- **`reglas_validacion` gained a `redondeo` column and `infraestructura` tipo_regla (2026-09-07, follow-up review)**: two defects found in the redesign below. (1) `tipo_calculo = personal_proporcional` was used for both Inicial's asistente ratios (COMPENDIO línea 422: "redondeo hacia arriba" — explicit) and Primaria's Educación Física rule (rounds down, per the floor decision below) with nothing in the schema distinguishing them — a naive engine implementation could not satisfy both, and using floor for Inicial would understaff a Lactantes room by half. Fixed by adding `redondeo VARCHAR(10) NOT NULL CHECK (redondeo IN ('arriba','abajo','na'))`; `'na'` for every non-`personal_proporcional` row (confirmed none of them divide anything, so none needed a rounding rule). (2) Three rows were misclassified under `tipo_regla = 'superficie'` despite measuring linear metres or book counts, not area (`primaria.superficie.altura_aulas`, `primaria.superficie.acervo_bibliografico`, `secundaria.superficie.acervo_bibliografico`) — added `'infraestructura'` to the `tipo_regla` CHECK and reclassified these three (new distribution: 16 superficie / 9 personal / 3 infraestructura = 28). Also fixed in the same pass: Primaria's PE rule previously combined `personal_proporcional` with a `condicion_min = 61` gate, producing a 0-to-2-teacher jump between 60 and 61 students — removed the gate, threshold now implicit via floor division. Created `app/Domain/Validaciones/Regla/CalculadoraRequerimiento.php`, the first real Motor de Validación code (pure, no DB), and rewired the seeder's boundary tests to exercise it instead of duplicating arithmetic inline. Full detail: `docs/reports/2026-09-07-reglas-validacion-schema.md`. The 60-vs-61 threshold question itself remains open — see `docs/decisions/PENDIENTE-umbral-educacion-fisica.md`, not resolved by this entry.
- **`reglas_validacion` schema redesigned (2026-09-07) before any engine code consumed it**: three defects fixed while the table still carried no production data. (1) Added `clave VARCHAR(100) UNIQUE NOT NULL` — a stable machine key (`{nivel}.{tipo_regla}.{slug}`) so the future Motor de Validación never has to switch on the free-text, accented `concepto` string. (2) Added `tipo_calculo` (9-value CHECK: `ratio_por_alumno`, `ratio_por_grado`, `minimo_fijo`, `adicional_fijo`, `factor`, `personal_obligatorio`, `personal_umbral`, `personal_proporcional`, `personal_por_espacio`) so the engine dispatches on an explicit calculation strategy instead of parsing `unidad` strings like `'trabajador social'`. (3) Added `ambito` (`aula`/`sala`/`plantel`/`escuela`/`predio`) disambiguating what `condicion_min`/`condicion_max` actually count — previously the same columns meant "aula capacity" for Inicial and "school enrollment" for Preescolar with nothing in the row saying which. `concepto` and `unidad` are now display-only. Also added `cargo_puesto_id` (nullable FK to `cargos_puestos`, left NULL — populating it is blocked on `CargosPuestosSeeder`'s data, not its schema). Migration (`2026_01_01_000010_create_reglas_validacion_table.php`) and `docs/ddl_sistema_incorporacion_v3.sql` edited in place (schema never deployed, no data to preserve). Two normative fixes surfaced during the redesign and confirmed against COMPENDIO §5.2 (Acuerdos Secretariales text, authoritative per the existing 2026-09-04 threshold decision): the Educación Física `condicion_min = 61` (>60) was re-verified as correct, not an off-by-one — §5.1's "60 alumnos o más" phrasing for Preescolar is the outlier COMPENDIO text, already superseded by the earlier decision. And Preescolar vs. Primaria Educación Física, previously seeded identically, are now split: Preescolar is `personal_umbral` (fixed 1 teacher once enrollment ≥61), Primaria is `personal_proporcional` (`ceil(enrollment / 60)` teachers, per §5.1's explicit "por cada 60... se puede requerir más de uno"). Seeder switched from delete-then-insert-per-nivel to `insertOrIgnore`, now safe since `clave` is UNIQUE. Full detail, the 28-row table, and taxonomy-fit notes: `docs/reports/2026-09-07-reglas-validacion-schema.md`. Follow-up: populate `cargo_puesto_id` once `CargosPuestosSeeder`'s Task 2 data exists in a form queryable by this seeder (currently no row links a `reglas_validacion` personal rule to a specific `cargos_puestos` row). **SUPERSEDED by the 2026-09-07 follow-up entry above: this entry's `ceil(enrollment / 60)` was a gate-plus-division defect (0-to-2-teacher jump at the 60/61 boundary) — the corrected formula is `floor`, not `ceil`. Do not follow the `ceil` guidance in this entry.**
- **`personal` columns made nullable for wizard draft rows (2026-09-07, branch `feat/wizard-progreso`)**: `cargo_puesto_id`/`nombre`/`nacionalidad`/`sexo`/`estudios`/`cedula_o_documento` dropped from `NOT NULL` (`escuela_nivel_id` stays `NOT NULL`) — explicitly authorized (not an ad hoc schema change) to support a resumable wizard where an applicant can save a half-filled Paso 3.5 (Plantilla docente) row and return later. This reopens the same hazard the `reglas_validacion` redesign was careful about: a table permissive enough to hold drafts must not let a draft silently look like real data to the Motor de Validación. Closed by `app/Domain/Personal/RegistroPersonalCompleto::esCompleto()` — a pure six-argument completeness check (all six non-null, and for the five string fields, non-empty-string) that the Motor's future personal-counting code **must** call before counting any `personal` row toward a staffing ratio; nothing calls it yet, since the counting logic itself is out of scope. Two new tables added in the same task, unrelated schema-wise but same authorization: `pasos_captura` (catalog of Paso 3's six sub-steps) and `escuela_nivel_pasos` (per-expediente sub-step progress, no code creates/advances rows yet). Full detail: `docs/reports/2026-09-07-wizard-progreso.md`. Follow-up left open: `escuela_nivel_pasos` has no per-nivel step-applicability model, so `mobiliario` (Educación Inicial only, per PRD §8) will get a row for every nivel unless whatever populates this table filters it — not decided.
- **ADR-001 (2026-09-07): the API-barrier's real-HTTP-round-trip design (D2) is dead, replaced with an in-process `app/Application/` layer**: the 2026-09-04 Opus review's finding (Livewire calling its own API by real HTTP can't work — no cookie jar server-side, `php artisan serve` is single-process, self-call deadlocks) is now a formal decision, not just an open finding. `docs/decisions/ADR-001-frontera-de-capas.md`: Livewire and the API controllers both call the same `app/Application/` use cases; the HTTP API is still built (versioned, OpenAPI via Scramble, contract-tested) but as a thin adapter for Etapa 3 external consumers, off the wizard's own path; boundary enforcement (Deptrac) deferred to after the MVP presentation, since static analysis over empty stubs proves nothing; the system is confirmed server-rendered (one route per wizard step, `redirect()` between steps), not a SPA. `docs/superpowers/specs/2026-09-04-api-layer-design.md`'s D2 and D3 annotated as superseded in place, original reasoning kept. No `app/Application/` code exists yet — this ADR sets the rule, doesn't implement it.
